# Assistant Designer GUI

Настольное приложение с графическим интерфейсом для работы с OpenAI API, анализа проектной и технической документации и выполнения многоэтапных сценариев обработки документов.

Приложение объединяет обычный чат с языковой моделью, загрузку файлов различных форматов, управление историей диалогов и сценарный конвейер анализа документов.

## Возможности

- чат с моделями OpenAI через `Chat Completions API`;
- потоковый и обычный вывод ответов;
- загрузка одного или нескольких документов;
- прикрепление содержимого файлов к сообщениям чата;
- извлечение текста и таблиц из PDF, DOCX и Excel;
- работа с TXT, Markdown, Python, JSON и CSV;
- многоэтапный анализ документов по JSON-сценариям;
- обработка нескольких документов совместно или по отдельности;
- объединение результатов отдельных этапов анализа;
- этапы без вызова LLM: конкатенация и заполнение шаблонов;
- поддержка системных и пользовательских промптов из Markdown-файлов;
- few-shot-примеры ответов для этапов сценария;
- автоматическое разбиение больших запросов на части;
- проверка и очистка JSON-ответов модели;
- повторные запросы при временных ошибках API;
- сохранение и загрузка истории диалогов;
- автоматическое краткое резюме диалога;
- экспорт результатов в TXT, Markdown, JSON, CSV, DOCX и XLSX;
- редактор сценариев;
- светлая и тёмная темы интерфейса;
- журналирование работы приложения.

## Назначение проекта

`Assistant Designer GUI` ориентирован на работу с технической документацией, но архитектура приложения не привязана к конкретной предметной области.

Типовые сценарии применения:

- анализ проектной документации;
- проверка документов по заданному перечню требований;
- извлечение структурированных данных;
- подготовка отчётов;
- сравнение нескольких документов;
- формирование сводного результата;
- последовательная обработка документа несколькими специализированными промптами;
- преобразование результата модели в Markdown, JSON, CSV, DOCX или XLSX.

### `gui`

Графический интерфейс приложения построен на `tkinter` и `ttkbootstrap`.

Главный класс `MainWindow` объединяет:

- чат;
- управление моделями и параметрами API;
- прикрепление файлов;
- работу с диалогами;
- выбор документов и сценариев;
- запуск и отмену анализа;
- отображение промежуточных результатов;
- сохранение и экспорт результатов;
- редактор сценариев;
- окно настроек.

### `core`

Модуль `core/chat_client.py` реализует асинхронный клиент OpenAI.

Запросы выполняются в отдельном потоке, поэтому графический интерфейс не блокируется во время ожидания ответа.

Клиент поддерживает:

- потоковую передачу ответа;
- callbacks для запуска, завершения, получения фрагментов и обработки ошибок;
- отмену текущего запроса;
- тестирование соединения;
- генерацию резюме диалога;
- адаптацию параметров под разные семейства моделей.

Для моделей с префиксами `o1`, `o3`, `gpt-4o` и `gpt-5` приложение заменяет `max_tokens` на `max_completion_tokens` и исключает параметры, которые код считает неподдерживаемыми.

### `document_handlers`

Подсистема преобразует документы в текстовое представление, пригодное для передачи языковой модели.

Поддерживаемые форматы:

| Формат | Обработка |
|---|---|
| PDF | текст и таблицы, разметка страниц |
| DOCX | абзацы, таблицы, колонтитулы и данные штампа |
| XLSX | листы и табличные данные |
| XLS | табличные данные старого формата Excel |
| TXT | текст |
| MD | текст Markdown |
| PY | исходный код как текст |
| JSON | текст или структурированные данные |
| CSV | текстовые табличные данные |

Для DOCX, PDF и текстовых документов результат преимущественно формируется в Markdown. Для Excel-файлов используется JSON-представление.

### `orchestrator`

Оркестратор выполняет анализ по сценарию.

Последовательность обработки:

1. загрузка JSON-файла сценария;
2. проверка его структуры;
3. загрузка связанных файлов промптов и шаблонов;
4. извлечение содержимого документов;
5. последовательное выполнение этапов;
6. сохранение промежуточных результатов;
7. формирование итогового ответа;
8. преобразование результата в требуемый формат.

Поддерживаются три режима этапа:

- `llm` — отправка запроса языковой модели;
- `concat` — объединение документа и результатов других этапов;
- `template` — заполнение текстового шаблона результатами предыдущих этапов.

### `config`

`ConfigManager` загружает настройки из `config.json`, создаёт конфигурацию по умолчанию при её отсутствии и читает API-ключ из `.env`.

### Хранение диалогов

`DialogManager` сохраняет каждый диалог в отдельный JSON-файл.

В диалоге могут храниться:

- сообщения пользователя и ассистента;
- временные метки;
- количество использованных токенов;
- резюме диалога;
- прикреплённые файлы;
- загруженные документы;
- загруженные сценарии;
- последний результат анализа.

## Требования

Рекомендуемая версия:

- Python 3.10 или новее;
- Windows, Linux или macOS;
- действующий API-ключ OpenAI;
- доступ к интернету для обращения к OpenAI API.

Для работы графического интерфейса Python должен быть установлен с поддержкой Tk.

В Linux пакет Tk может потребовать отдельной установки:

```bash
sudo apt install python3-tk
```

## Установка

### 1. Клонирование репозитория

```bash
git clone https://github.com/ehfrosee/Assistant_designer_GUI.git
cd Assistant_designer_GUI
```

### 2. Создание виртуального окружения

Windows PowerShell:

```powershell
python -m venv .venv
.venv\Scripts\Activate.ps1
```

Windows Command Prompt:

```cmd
python -m venv .venv
.venv\Scripts\activate.bat
```

Linux или macOS:

```bash
python3 -m venv .venv
source .venv/bin/activate
```

### 3. Установка зависимостей

```bash
python -m pip install --upgrade pip
pip install -r requirements.txt
```

### 4. Установка PyMuPDF

PDF-процессор импортирует модуль `fitz`, предоставляемый пакетом `PyMuPDF`. В текущем `requirements.txt` этот пакет не указан, поэтому его необходимо установить отдельно:

```bash
pip install PyMuPDF
```

Без `PyMuPDF` метод `PDFProcessor.can_process()` возвращает `False`, даже если установлен `pdfplumber`.

### 5. Настройка API-ключа

Создайте файл `.env` в корневом каталоге проекта:

```env
OPENAI_API_KEY=your_openai_api_key
```

Не добавляйте `.env` в систему контроля версий.

API-ключ также можно сохранить через окно настроек приложения.

## Запуск

Запускайте приложение из корневого каталога проекта:

```bash
python main.py
```

После запуска:

1. приложение загрузит `config.json`;
2. при отсутствии `.env` создаст пустой файл;
3. создаст необходимые рабочие каталоги;
4. проверит наличие API-ключа;
5. выполнит тестовое подключение к OpenAI;
6. загрузит доступные модели;
7. откроет главное окно.

## Работа с чатом

В режиме чата можно:

1. выбрать модель;
2. изменить параметры генерации;
3. ввести запрос;
4. прикрепить один или несколько файлов;
5. отправить запрос;
6. остановить текущую генерацию;
7. сохранить выделенный текст или разделы ответа.

Прикреплённые документы преобразуются в текст и добавляются в контекст запроса.

История текущего диалога автоматически сохраняется в каталоге `dialogs`.

## Анализ документов по сценарию

Сценарий описывает последовательность операций над документом.

Приложение поддерживает:

- один документ;
- несколько документов;
- совместную обработку документов;
- отдельную обработку каждого файла;
- дополнительный этап агрегации;
- зависимости между этапами;
- разные модели и параметры для отдельных этапов;
- текстовый, Markdown- или JSON-результат.

### Общая структура сценария

```json
{
  "name": "Document analysis",
  "description": "Example multi-stage analysis",
  "files_processing": {
    "mode": "combined",
    "aggregate_stage": null
  },
  "stages": [
    {
      "id": "extract_requirements",
      "processing_mode": "llm",
      "input": {
        "source": "document"
      },
      "system_prompt": "extract_requirements_system",
      "prompt_template": "extract_requirements_user",
      "format_examples": "extract_requirements_examples",
      "output_format": "json",
      "params": {
        "model": "gpt-4o-mini",
        "temperature": 0.2,
        "max_tokens": 4000,
        "timeout": 180
      }
    }
  ]
}
```

Связанные Markdown-файлы должны находиться в том же каталоге, что и JSON-файл сценария:

```text
scenarios/
└── requirements_analysis/
    ├── scenario.json
    ├── extract_requirements_system.md
    ├── extract_requirements_user.md
    └── extract_requirements_examples.md
```

Расширение `.md` в ссылках можно не указывать.

## Поля этапа сценария

### `id`

Уникальный идентификатор этапа:

```json
"id": "extract_requirements"
```

На результат этапа можно ссылаться через:

```text
stage.extract_requirements
```

### `processing_mode`

Режим выполнения:

```json
"processing_mode": "llm"
```

Допустимые значения:

- `llm`;
- `concat`;
- `template`.

Если поле отсутствует, используется `llm`.

### `input.source`

Источник входных данных этапа.

Исходный документ:

```json
"input": {
  "source": "document"
}
```

Результат предыдущего этапа:

```json
"input": {
  "source": "stage.extract_requirements"
}
```

Несколько источников:

```json
"input": {
  "source": [
    "document",
    "stage.extract_requirements"
  ]
}
```

При нескольких источниках содержимое объединяется разделителем.

### `system_prompt`

Ссылка на Markdown-файл системного промпта:

```json
"system_prompt": "extract_requirements_system"
```

Файл:

```text
extract_requirements_system.md
```

### `prompt_template`

Ссылка на Markdown-файл пользовательского промпта:

```json
"prompt_template": "extract_requirements_user"
```

Для подстановки содержимого используется маркер:

```text
{content}
```

Пример файла:

```markdown
Проанализируй документ и извлеки требования.

Документ:

{content}
```

### `format_examples`

Необязательный файл few-shot-примеров. Он преобразуется в последовательность сообщений `user` и `assistant`.

```json
"format_examples": "extract_requirements_examples"
```

### `output_format`

Формат ответа этапа:

```json
"output_format": "json"
```

Типичные значения:

- `text`;
- `markdown`;
- `json`.

При формате `json` анализатор пытается:

1. удалить Markdown-ограждение;
2. извлечь JSON из текста;
3. проверить результат через `json.loads`;
4. повторить запрос при невалидном JSON.

### `params`

Параметры конкретного этапа переопределяют общие настройки:

```json
"params": {
  "model": "gpt-4o-mini",
  "temperature": 0.2,
  "max_tokens": 4000,
  "timeout": 180
}
```

## Режим `concat`

Режим объединяет содержимое нескольких источников без обращения к OpenAI API.

```json
{
  "id": "combine",
  "processing_mode": "concat",
  "input": {
    "source": [
      "stage.first",
      "stage.second"
    ]
  },
  "output_format": "text"
}
```

## Режим `template`

Режим заполняет Markdown-шаблон результатами других этапов.

Сценарий:

```json
{
  "id": "build_report",
  "processing_mode": "template",
  "input": {
    "source": [
      "stage.summary",
      "stage.issues"
    ]
  },
  "template_file": "report_template",
  "output_format": "text"
}
```

Файл `report_template.md`:

```markdown
# Отчёт

## Резюме

{{ stage.summary }}

## Найденные замечания

{{ stage.issues }}
```

## Шаблон вывода LLM-этапа

Для LLM-этапа можно указать `output_template`. Если ответ является JSON, значения подставляются по ключам:

```json
{
  "output_template": "result_template"
}
```

Пример шаблона:

```markdown
# Результат

**Статус:** {{ status }}

**Заключение:** {{ conclusion }}
```

Поддерживаются вложенные пути:

```text
{{ project.metadata.code }}
```

## Обработка нескольких файлов

### Совместная обработка

```json
"files_processing": {
  "mode": "combined"
}
```

Содержимое файлов объединяется и передаётся в один конвейер:

```text
--- Документ 1: path/to/file1.pdf ---
...

--- Документ 2: path/to/file2.docx ---
...
```

### Раздельная обработка

```json
"files_processing": {
  "mode": "separate",
  "aggregate_stage": "merge_results"
}
```

Каждый файл проходит этапы до `merge_results` отдельно. Затем результаты объединяются и передаются в этап агрегации.

Если `aggregate_stage` не задан, приложение возвращает JSON со списком результатов для всех файлов.

## Разбиение больших документов

`Analyzer` оценивает количество токенов пользовательского промпта через `tiktoken`.

При превышении внутреннего порога запрос разбивается по абзацам. Каждый фрагмент анализируется отдельно, после чего ответы объединяются:

- текстовые ответы — через двойной перенос строки;
- JSON-ответы — в JSON-массив.

Текущая реализация использует внутренний безопасный порог `20 000` токенов, независимо от значения `analysis.chunk_size_tokens` в `config.json`.

Следует учитывать, что простое объединение ответов не является полноценным reduce-этапом. Для качественной обработки больших документов рекомендуется создавать отдельный этап агрегации в сценарии.

## Конфигурация

Основные настройки находятся в `config.json`.

Пример:

```json
{
  "llm_defaults": {
    "model": "gpt-4o-mini",
    "temperature": 0.3,
    "max_tokens": 10000,
    "timeout": 180
  },
  "paths": {
    "scenarios_dir": "./scenarios",
    "rag_db_dir": "./rag_db",
    "logs_dir": "./logs",
    "env_file": ".env"
  },
  "rag": {
    "embedding_model": "text-embedding-ada-002",
    "top_k": 5,
    "vector_db_type": "faiss"
  },
  "ui": {
    "theme": "light",
    "language": "ru"
  },
  "dialog": {
    "history_pairs": 3,
    "summary_pairs": 3,
    "summary_model": "gpt-4o-mini"
  },
  "processing": {
    "enable_chunking": true,
    "chunk_size_tokens": 5000,
    "chunk_overlap_tokens": 200
  }
}
```

### Основные секции

| Секция | Назначение |
|---|---|
| `llm_defaults` | модель и общие параметры API |
| `paths` | рабочие каталоги и путь к `.env` |
| `ui` | тема и язык интерфейса |
| `dialog` | параметры истории и суммаризации |
| `processing` | параметры разбиения документов |
| `analysis` | параметры сценарного анализа |
| `rag` | задел для конфигурации RAG |

Настройки `rag` присутствуют в конфигурации, однако полноценный RAG-конвейер в текущей структуре репозитория не подключён к оркестратору.

```

Основной журнал:

logs/app.log
```

## Экспорт результатов

Интерфейс позволяет сохранять:

- полный ответ;
- выделенный фрагмент;
- разделы ответа, размеченные строками `--- имя_файла`;
- результаты анализа.

В зависимости от команды доступны форматы:

- TXT;
- Markdown;
- JSON;
- CSV;
- DOCX;
- XLSX.

Модуль `Reporter` поддерживает преобразование JSON-массива объектов в Markdown-таблицу или CSV.

## Ограничения текущей версии

### PyMuPDF отсутствует в `requirements.txt`

`PDFProcessor` требует одновременно `pdfplumber` и `fitz`, но пакет `PyMuPDF`, предоставляющий `fitz`, не указан в зависимостях.

Установите его вручную:

```bash
pip install PyMuPDF
```

### OCR фактически не подключён

В `requirements.txt` указан `pytesseract`, однако текущий `PDFProcessor` извлекает текст через `pdfplumber` и `PyMuPDF`. Автоматическое OCR сканированных страниц в показанном конвейере не реализовано.

Для сканированных PDF результат может быть пустым или неполным.

### Tesseract устанавливается отдельно

Даже после реализации OCR библиотека `pytesseract` требует установленного системного приложения Tesseract OCR.

### Настройки RAG пока не используются

В конфигурации и зависимостях присутствуют параметры ChromaDB, FAISS-подобной конфигурации и эмбеддингов, но в текущем оркестраторе нет рабочего RAG-пайплайна.

### Несогласованность конфигураций

`config.json` и `config/default_config.py` содержат разные значения и частично разные поля. Например:

- отличаются `max_tokens` и `timeout`;
- различаются размеры чанков;
- некоторые пути присутствуют только в конфигурации по умолчанию;
- секция `analysis` присутствует в корневом конфиге, но отсутствует в `default_config.py`.

При существующем `config.json` используется именно он. Конфигурация по умолчанию применяется только при отсутствии файла.

### PyQt6 не используется основной точкой входа

`requirements.txt` содержит `PyQt6`, но `main.py` запускает интерфейс `MainWindow`, построенный на Tkinter/ttkbootstrap. Для основного сценария запуска PyQt6, вероятно, не требуется.

### Ограниченная отмена API-запросов

Отмена устанавливает внутренний флаг и прекращает обработку следующих фрагментов или streaming-ответа. Уже отправленный синхронный HTTP-запрос может продолжать выполняться до ответа или тайм-аута.

### Используется Chat Completions API

Клиент построен на `client.chat.completions.create()`. Новые возможности Responses API в текущей версии не используются.

## Диагностика

### Ошибка `OPENAI_API_KEY не найден в .env`

Проверьте, что файл `.env` находится в корне проекта:

```env
OPENAI_API_KEY=your_openai_api_key
```

Запускайте приложение из корневого каталога:

```bash
python main.py
```

### PDF-файл не открывается

Установите обе зависимости:

```bash
pip install pdfplumber PyMuPDF
```

### Ошибка `_tkinter` или отсутствует Tk

Ubuntu/Debian:

```bash
sudo apt install python3-tk
```

Для Windows используйте официальный установщик Python с включённым компонентом Tcl/Tk.

### Не найден файл промпта сценария

Все файлы, указанные в `system_prompt`, `prompt_template`, `format_examples`, `output_template` и `template_file`, должны находиться рядом с JSON-файлом сценария.

Пример:

```text
scenario.json
system_prompt.md
user_prompt.md
examples.md
report_template.md
```

### Модель отклоняет параметры запроса

Проверьте настройки этапа и общую конфигурацию. Разные модели поддерживают разные параметры и ограничения.

Адаптация параметров в проекте основана на префиксе имени модели и может потребовать обновления при добавлении новых моделей.

### Невалидный JSON после нескольких попыток

Упростите формат ответа и явно укажите JSON-схему в системном или пользовательском промпте. Для сложных результатов полезно разделить извлечение данных и формирование отчёта на разные этапы.

## Разработка

### Добавление нового процессора документов

1. Создайте класс-наследник `BaseDocumentProcessor`.
2. Реализуйте:
   - `can_process(file_path)`;
   - `extract_content(file_path)`.
3. Добавьте процессор в `_get_processors()` файла `document_handlers/adapter.py`.
4. Добавьте расширение в `FileLoader`.
5. Добавьте необходимую библиотеку в `requirements.txt`.

Минимальный каркас:

```python
from document_handlers.base_processor import BaseDocumentProcessor


class CustomProcessor(BaseDocumentProcessor):
    def can_process(self, file_path: str) -> bool:
        return file_path.lower().endswith(".custom")

    def extract_content(self, file_path: str) -> str:
        with open(file_path, "r", encoding="utf-8") as file:
            return file.read()
```

### Добавление нового режима этапа

Новый режим обработки добавляется в функцию `_execute_stage()` файла:

```text
orchestrator/dispatcher.py
```

Режим должен вернуть словарь:

```python
{
    "content": result_text,
    "format": "text",
    "formatted_content": result_text
}
```
